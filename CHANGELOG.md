# Changelog

Notable changes, newest first. There are no versions: each entry is headed by the date it reached `main`, as `## YYYY-MM-DD`.

An entry that needs changes by hand in a project's own files has an `### Upgrading` section. `dart tool/upgrade.dart` prints the ones dated on or after the project's last framework change.

## 2026-11-11

### Added
- `flutter_agentify_core`: a schema builder, actions and their registry (approval gate, timeouts, redaction, change events, receipts), app context with `view_screen` and `navigate`, the agent loop (retries, stop limits, approval, tool search, answer-only mode, history summaries), OpenAI-compatible and Anthropic providers with presets, thread and memory stores with a shared contract, the action CLI helper, the action reference generator, the parity check, docs search and the doctor
- `flutter_agentify_ui`: the assistant's chat widget and controller, approval cards, receipt chips and a debug inspector
- `flutter_agentify_on_device`: a model that runs inside the app, Gemma 4 E2B (about 2.6 GB, no Hugging Face token, pinned revision) on Google's LiteRT-LM through `flutter_edge_ai` 2.6.0 and `flutter_edge_ai_litertlm` 1.20.0 (exact pins). Its provider keeps the engine's chat warm between steps and replays the history only when it must; the GPU runs at float32, which keeps long ids intact
- One setup file, `lib/ai/assistant_setup.dart`, chooses where the model runs: `ModelMode.server`, `ModelMode.onDevice` or `ModelMode.both` (the in-app model once it is ready, the server until then), with the in-app model's download consent and web switch, and the server's defaults. `ServerSetup(userEditable: false)` hides the server settings and leaves `set_assistant_provider` and `set_api_key` unregistered; the gate checks that the file is consistent
- The in-app model in the chat and Settings: a download card with the size and Not now, a Model on this device block in Settings with the model's name, size and state, a progress bar with Cancel, Getting ready, Retry, and Download and Delete buttons that ask first in a dialog naming the model and its size, the answering model in the chat header (for example "Gemma 4 E2B · On this device" or "Ollama · llama3.2"), a line when the device takes over, and a card that asks before a conversation answered on the device goes to a server (remembered per conversation in the database). In `both`, an Answers with choice in Settings (This device or Model server), and a switch in the chat's model menu, let the person have the server answer instead; the assistant can change it with `set_use_on_device_model`. On web, where the in-app model is off by default (`enableOnWeb`), `both` hides the on-device settings and uses the server. It loads when the assistant first opens, not at app start; a load that never finished (the app was killed for memory) is not retried by itself. Four UI-only actions: `download_on_device_model`, `cancel_on_device_model_download`, `delete_on_device_model` and `dismiss_on_device_offer`. Core has the engine-free parts and a `FakeOnDeviceEngine` for tests
- `tool/measure_on_device.sh -d <device>`, which runs ten fixed requests on the in-app model and prints one row for the measured table in the guide to where the model runs
- `flutter_agentify_lints`, an analyzer plugin whose rules run in `dart analyze` and the IDE: `domain_layer_boundaries`, `presentation_layer_boundaries`, `ui_calls_actions`, `no_error_returns_in_actions`, `no_hardcoded_colors`, `no_hardcoded_strings`, `no_navigator_push`, `no_raw_sql_interpolation` and `no_secret_literals`
- Two starting points for a new app, both running on actions: `example`, a list of items plus settings, and `empty`, which starts clean and keeps the item example as reference in `.agents/example/`. Both have `set_theme_mode`, `set_language`, `set_assistant_provider` and `set_api_key`; `example` adds `list_items`, `get_item`, `create_item`, `update_item`, `delete_item` and `delete_items`. `tool/action.dart` runs them without the UI
- The assistant in the app: a side panel on wide screens and a sheet on narrow ones, kept across navigation; model settings with presets; one key per provider in secure storage (never on web); assistant threads and memories in drift
- The chat: a thinking indicator while the model works, tool rows with readable action names, an approval card with a summary and details (a red Approve for actions that cannot be undone), a badge on the assistant button while an approval waits, receipts under the reply in the app's language (an action's receipt names a `receipt_<key>` translation, with the English summary as fallback), a Conversations sheet, Enter to send on desktop and web, Stop, and Continue after a step limit. Errors have a kind (connection, timeout, key, model not found, rate limit, server, refused request, bad reply) and show a translated message with a next step, Retry when it may help and Open settings when the setting is the cause. A request that receives nothing for 120 seconds stops with a timeout
- Screens: Home with an item list (edit and delete buttons on each row, select by long press, delete the selected rows), Settings with model settings that show errors under the field, a language picker with each language in its own name, and light, dark and system themes
- `tool/check.sh`, the single gate: code generation, schema dump, format, analyze, every test suite and the doctor
- The doctor (`dart run flutter_agentify_core:doctor`): checks for the agent files, skills, bundled secrets, additive migrations, and a ratchet on `// ignore:`, `!` and `dynamic`; the parity test (`test/ai/parity_test.dart`)
- `AGENTS.md`, with `CLAUDE.md` and `GEMINI.md` importing it, a shared `.agents/skills/` folder with a skill per topic, and `learnings.defaults.md`
- Drift schema dumps in `drift_schemas/`
- Languages defined in one list, `kSupportedLanguages` in `lib/domain/entities/language/supported_languages.dart`: each entry has its code, names and font, the first is the default, and the text direction follows the code. English and Persian (Farsi, right to left) ship, with Inter and Vazirmatn fonts under the SIL Open Font License. The translation and layout tests run for every language in the list
- Android, iOS, macOS, Linux, Windows and web targets, with iOS local-network access for a model server on the same network
- A GitHub Actions workflow that runs the gate for the template and both starting points and builds each platform, contributing guidelines, a Code of Conduct, a security policy, and issue and PR templates
- `tool/setup.dart`, which turns a copy of the template into a named project: package name, organization, title and app ids, the chosen starting point, where the model runs (`--model server|both|on-device`, default `server`, with the platform floors the in-app model needs), and a README for the new project. It refuses unsafe names and titles, has `--dry-run` and `--reset-git`, and needs no `pub get`
- `tool/upgrade.dart`, which brings the newest framework from `main` (or a chosen commit with `--ref`) into a project: it replaces the packages, the framework's skills and `learnings.defaults.md`, and prints the steps to make by hand
- `tool/check_template.sh`, which sets up both starting points, each with a server only and with the in-app model (and the example with only the in-app model), in temp copies and runs each one's gate, then follows the feature tutorial on a new empty project and runs its gate
- macOS debug builds are signed to run locally (ad hoc), which the in-app model's engine needs; the app sandbox is on in debug builds too
- Documentation for people in `docs/`: getting started, concepts, guides, a reference index, and two tutorials (a feature by hand, and the same feature built by a coding agent)
- The doctor's `doc-links` check, which fails when a relative link in the root Markdown files, `docs/`, or the packages' READMEs and `doc/` pages points at a missing file
- The skill-command test: the parity test fails when a command in a skill or `AGENTS.md` names an action that does not exist or a test file that is missing
